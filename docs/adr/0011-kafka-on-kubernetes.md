# ADR 0011 — Kafka on Kubernetes: Strimzi in opspilot-data, one KRaft node, topics as KafkaTopic objects

- **Status:** Accepted
- **Date:** 2026-11-10

## Context
Step 4.3 brings Kafka to the kind cluster. The architecture names Strimzi (B8: "Kafka KRaft, 1 broker"). Locally Kafka
must behave like the Compose one (step 2.1):
- Kafka 4.2.2, the version of the client inside our services
- KRaft mode on one node
- the 8 topics of B2.2 with 3 partitions each
- no automatic topic creation
- a plain listener with no login

The Mac is short on memory (ADR 0009, decision: stay local while Docker stays under ~4.3 GB).

## Decision
1. **The Strimzi operator 1.3.0** (Helm chart from `oci://quay.io/strimzi-helm`, operator image pinned by digest) is
   installed by `kind-up.sh` into **`opspilot-data`**, next to CloudNativePG.
   - It watches only that namespace (the chart's default): its rights to Pods, Secrets etc. are RoleBindings there.
   - It keeps a few cluster-wide rights: list nodes, read StorageClasses, create ClusterRoleBindings. Kubernetes'
     escalation check only lets it grant rights it already holds.
   - Version: 1.3.0 (2026-10-12) supports Kafka 4.2.2 and Kubernetes ≥ 1.32. 1.3.1 (2026-11-04: dependency updates,
     Kafka 4.3.2) was 6 days old, too new for our two-week rule; upgrade once it qualifies.
2. **Strimzi's "restricted" pod security provider** (`STRIMZI_POD_SECURITY_PROVIDER_CLASS=restricted`). Every pod it
   creates gets the settings Pod Security "restricted" asks for; without it, `opspilot-data` would refuse them.
3. **Our chart `deploy/helm/kafka`:**
   - a `KafkaNodePool` with **one node, controller + broker** (KRaft): heap 512 MB as in Compose, memory limit 1 GiB,
     2 GiB disk shared by messages and KRaft metadata
   - a `Kafka` 4.2.2 (metadata version `4.2-IV1`; Strimzi's image for 4.2.2 pinned by digest)
   - a **plain internal listener on 9092**, with no TLS and no login, like Compose. NetworkPolicies limit who may
     connect (4.5). Strimzi adds its own TLS listener for controller and replication traffic.
   - broker settings as in Compose: one copy of the internal topics, `auto.create.topics.enable: false`, no initial
     rebalance delay
   - **only the Topic Operator**: there are no Kafka logins for the User Operator to manage, and it would cost memory
   - the 8 topics as **`KafkaTopic` objects** (3 partitions, 1 replica). The list is a chart value, kept in step with
     `deploy/docker/kafka/topics.txt` for Compose.
   - a `helm test` pod with the checks of Compose's `smoke-test.sh`
4. Clients connect to `kafka-kafka-bootstrap.opspilot-data.svc:9092`. The release name names the cluster; Strimzi
   adds `-kafka-bootstrap`.

## Alternatives considered
| Option | Why not chosen |
|---|---|
| The official `apache/kafka` image as our own StatefulSet (as Compose does) | No operator to learn from or fight with, but we would hand-write what Strimzi does: KRaft node ids, rolling restarts after a config change, topic management, certificates for internal traffic. B8 names Strimzi, and its `KafkaTopic` objects put topics in Git (GitOps, Phase 5). |
| Topics created by a one-off Job running `kafka-topics.sh` (like Compose's `kafka-init`) | Works once, but nothing keeps the topics as declared afterwards; a `KafkaTopic` is reconciled. |
| Strimzi 1.3.1 | Too new for our two-week rule when this was built. |
| Kafka 4.3 | Our services' client is 4.2.2; broker and client on the same version, as in Compose. |
| The User Operator, a TLS/SCRAM listener now | No Kafka logins exist yet; adding them means service-side changes. Left as a known gap with NetworkPolicies (4.5) as the guard. |

## Consequences
- **Measured (2026-11-10, M2, Docker 4.8 GB):**
  - `kind-up.sh` (now with two operators) took 204 s.
  - Kafka was `Ready` 264 s after the charts were sent, mostly image downloads.
  - Memory: broker 466 MiB, Strimzi operator 271 MiB, Topic Operator 156 MiB. The node went from 1.23 GiB to
    2.06 GiB (+0.83 GiB); Docker as a whole is at ~2.5 of 4.8 GB, under ADR 0009's 4.3 GB rule.
- **`helm test kafka`: 13/13 checks pass in 19 s**
  - 8 topics with 3 partitions
  - three keys, each in one partition and in order
  - a misspelled topic refused and not created
- **Two mutations were caught:**
  - a topic with 4 partitions → 1 FAIL
  - auto-create on → 2 FAILs; Strimzi restarted the broker by itself in 26 s
- **Partitions can only grow.** Going back from 4 to 3, the `KafkaTopic` turned `NotSupported: Decreasing partitions
  not supported`. The way back is to delete the topic (the Topic Operator deletes it in Kafka) and recreate it, which
  loses its messages.
- **A deleted broker pod** was back in 23 s; a message written before was read back, and all 8 topics were still
  there (PersistentVolumeClaim `data-0-kafka-dual-role-0`).
- **Generated by Strimzi:**
  - PodDisruptionBudgets for Kafka (`minAvailable: 0` for the one broker, so maintenance isn't blocked)
  - NetworkPolicies that open 9092 to every pod. Step 4.5's default-deny has to work with these.
- The Kafka container is not read-only (Strimzi's restricted provider doesn't set it); "restricted" doesn't require
  it.
- Deleting a `KafkaTopic` (e.g. `helm uninstall kafka`) deletes the topic and its messages.
